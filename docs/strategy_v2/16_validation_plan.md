# 16_validation_plan.md — 検証計画とプロジェクトサマリー

## 最も重要な仮説 TOP5

1. **「価値を先に見せる」ことで、無入力状態でも受け手は自分ごと化できる**
   会社名と業種の言及だけで、テンプレート営業メールとの違いを一瞬で認識してもらえるか。
   これが崩れると本コンセプトの前提自体が成立しない。
2. **薄い公開情報だけから、送るに値する精度のレポートを生成できる**
   プロフィール入力がない分、入力情報はドメイン起点の推測に依存する。
   関連度の低い当て推量を送ってしまうと、逆に「テンプレ営業」以下の印象を与えるリスクがある
   （[05_ai_pipeline.md](05_ai_pipeline.md)の④関連度判定の精度が事業の生命線）。
3. **Human in the Loopを維持したまま、経済的に成立する運用ができる**
   1件あたりレビュー5〜10分という制約の中で、送信数・反応率・成約率が
   事業として十分な規模になるか（[06_human_review.md](06_human_review.md)、[12_operations.md](12_operations.md)）。
4. **無料レポート単体が、登録・有料化への十分な動機になる**
   「もっと詳しく見たい」という欲求が自然発生するか、それとも無料版だけで満足されて
   終わってしまうか（[07_free_report.md](07_free_report.md)、[08_paid_report.md](08_paid_report.md)）。
5. **適法な経路だけでも、事業として十分な量のリードを獲得できる**
   特定電子メール法の適用除外（公表アドレス）と紹介・問い合わせ経由だけで、
   スケール可能な量のターゲットにリーチできるか（[03_lead_generation.md](03_lead_generation.md)）。

## 最初の1か月で検証すべきこと TOP10

1. 手動で作成したレポート10〜20件を実際に送り、開封率・返信率を計測する（Phase 0）
2. 受け手から「自分向けだと感じた」という直接的な反応が得られるかヒアリングする
3. 関連度判定の精度（薄い根拠での的外れな提案がどれくらいの割合で発生するか）を確認する
4. レビューにかかる実時間を計測し、1件あたりのコストを試算する
5. どの業種（税理士/建設/補助金/法改正/バックオフィス）で最も反応が良いかを比較する
6. 無料レポートから登録への転換率を計測する（簡易LPで良い）
7. 「いくらなら払うか」を、反応の良かった企業への個別ヒアリングで探る（[09_pricing.md](09_pricing.md)）
8. 適法に取得できるターゲットリストの実数を確認する（想定より少ない場合、経路の見直しが必要）
9. 誤送信・誤情報のリスクが実際にどの工程で発生しやすいかを洗い出す（[14_risk.md](14_risk.md)）
10. ChangeScoutの市場変化データベースがAORの③市場変化抽出にそのまま使えるか、
    データ形式・カバレッジを確認する（[13_architecture.md](13_architecture.md)）

## 既存ChangeScoutとの役割分担

| | ChangeScout | AI Opportunity Report（AOR） |
|---|---|---|
| 役割 | プロダクト本体（継続利用されるSaaS） | 新規顧客獲得のための営業エンジン（リードジェネ） |
| フロー | プル型（ユーザーが入力し取りに行く） | プッシュ型（こちらから価値を先出しする） |
| KPI | 継続利用率・MRR | 登録転換率・有料化率・商談化数 |
| 共有資産 | 市場変化データベース、企業解析エンジン（将来） | 同左 |

AORは「ChangeScoutの入口」として設計されており、競合するプロダクトではない。
PROJECT.mdの「First Priority: 最初の顧客を見つけること」という原則に対して、
AORは**顧客発見の仕組みそのもの**を担う。ChangeScoutが「作った後に売る」ボトルネックを
抱えていたとすれば、AORはその手前の「見つけて、価値を証明してから売る」を担当する。

## 将来的に統合するなら、どのような形が望ましいか

1. **データ層の統合を先に行う**: 市場変化データベース・企業解析エンジンをまず共通化する。
   プロダクトのUI/UXはしばらく分けたままでよい（[13_architecture.md](13_architecture.md)）。
2. **AORをChangeScoutの「営業チャネル」として位置づける**: AOR経由で登録した企業には、
   初回から「あなたの会社の分析はすでに一部終わっています」という状態でChangeScoutの
   プロフィール入力を大幅に省略した状態で迎える（AORの解析結果をChangeScoutの初期入力として流用する）。
   これにより、ChangeScout側の「入力を求められる前に離脱する」課題も同時に緩和できる。
3. **UIの統合は最後でよい**: 無理に単一プロダクトへ早期に統合せず、
   「AOR = 獲得」「ChangeScout = 継続利用」という役割の違いが実データで裏付けられてから
   プロダクト統合を検討する。

## 検証の進め方

- Phase 0（[15_roadmap.md](15_roadmap.md)）は数字ではなく「定性的な手応え」を最優先で見る
- 定量指標が意味を持つのは、送信件数が最低でも数十件を超えてから
- 仮説が崩れた場合（例: 精度が出せない、適法なリードが集まらない）は、
  無理にPhaseを進めず、コンセプト自体の再検証に戻る
