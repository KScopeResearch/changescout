# メール回収・顧客導線 本番化設計レビュー（Task27）

本ドキュメントは実装ではなく設計レビュー。メール保存・送信機能は今回実装していない
（意図的。厳守事項により禁止されている）。目的は、現状を正確に把握し、将来の
実装判断に必要な材料を揃えること。

## ①現在のメール回収フローの全体像

```
website/aor/report-preview.html?company=<slug>
  （無料レポート。free_opportunity 1件をフル表示、残りはロック表示）
        │
        │ CTA「追加分析を見る（無料）」クリック
        │ href = email-capture.html?company=<slug>（encodeURIComponent済み）
        ▼
website/aor/email-capture.html?company=<slug>
  （同じ data/<slug>.json を再取得し、会社名・業種をフォームへ事前入力）
        │
        │ メールアドレス入力 → 送信（ブラウザの既定送信はpreventDefaultで停止）
        │ HTML5 checkValidity() でクライアント側検証のみ。ネットワーク送信は無い
        ▼
   成功画面（同一ページ内、DOM書き換えのみ）
        │  free_opportunity.extended_analysis を表示
        │  「確認メールを<email>宛に送信しました（本モックでは実際のメール送信は
        │    行われません）」という文言を明示
        │
        │ CTA「さらに詳しい分析を見る」クリック
        │ href = paid-preview.html?company=<slug>
        ▼
website/aor/paid-preview.html?company=<slug>
  （有料版全内容。決済は無く、mailtoリンクでの問い合わせのみ）
```

**slugの受け渡し**: 3画面すべてが`?company=<slug>`というURLクエリパラメータのみで
状態を共有している。サーバーセッション・Cookie・localStorageは一切使わない
（3画面は完全にステートレスな独立ページとして設計されている）。

**メールアドレスの扱い**: `email-capture.js`の`emailInput.value`はJavaScript変数上に
一時的に存在するのみ。`showSuccess(email)`が呼ばれた時点で、その値は
`document.getElementById('success-email').textContent`へコピーされ画面に表示される
（ユーザー自身が今入力した値を、確認として見せているだけ）。ページを離れる・
再読み込みすると値は失われる。送信・保存を行うコード（`fetch`・`XMLHttpRequest`・
`localStorage.setItem`・`sessionStorage.setItem`・`document.cookie =`）は
`website/aor/assets/js/`配下のいずれのファイルにも存在しない
（`grep`で実際に0件を確認済み）。

## ②コード・ブラウザによる現状確認

- コード調査: `report-preview.js`（`wireCtas()`でCTAのhref組み立て）、
  `email-capture.js`（フォーム送信ハンドラ、`showSuccess()`）、`common.js`
  （`getCompanyParam()`・`fetchCompanyData()`・`mailtoLink()`）を全件確認
- ブラウザ実測: 仮のメールアドレス`e2e-test@example.com`（実在の個人アドレスは
  不使用）を実際に入力・送信し、以下すべてで痕跡が無いことを確認した
  - Console: エラー・警告なし
  - Network: 送信後の新規リクエストなし（初回ページロード時の`data/<slug>.json`
    取得のみ）
  - localStorage / sessionStorage / Cookie: 送信前後とも空
  - URL: 送信してもクエリパラメータ・ハッシュに変化なし
  - DOM: `#success-email`要素にのみ表示（同一タブ内、一時的）
  - `scripts/generator/logs/`・`backup/`・`website/aor/data/`: リポジトリ全体を
    `grep`し、入力したメールアドレス文字列が一切存在しないことを確認した

**結論**: 現状のメール回収フローは、実装上も実測上も、完全に副作用のない
静的モックである。個人情報保護の観点からは現時点で最も安全な状態にある
（存在しないデータは漏洩しようがない）。

## ③利用者から見た無料→有料導線評価

UIは変更していない。以下は観察記録のみ。

**良い点**:
- 各段階のCTA文言が一貫して具体的（「追加分析を見る（無料）」→
  「詳細レポートを受け取る」→「さらに詳しい分析を見る」→「有料プランに申し込む」）。
  「次に何が起きるか」が概ね予測できる文言になっている
- メール送信の「約束」について、実装と表示が意図的に一致させてある
  （「確認メールを送信しました」の直後に「本モックでは実際のメール送信は
  行われません」と明記。ユーザーを誤解させない透明性のある設計）
- 価格帯（「月額数千円〜1万円台（目安）」）を隠さず表示している
- 決済が無いことも明示している（「オンライン決済は行われません。
  お申し込み後、担当者よりご連絡します」）
- 「申し込む」だけでなく「営業担当に相談する」という低コミットメントの
  選択肢も用意されている

**記録すべき懸念点（UIは変更しない）**:
1. 価格帯が「月額数千円〜1万円台」とかなり幅広く、購入検討の材料としては
   曖昧。本番化時は具体的な価格またはプラン別価格表が必要になる可能性がある
2. 無料版と有料版の違いが、ロック表示（🔒）と価格パネルから間接的に読み取れる
   のみで、機能比較表のような明示的な対比は無い
3. `email-capture.html`の同意チェックボックスが指す「プライバシーポリシー」
   リンクは`href="#"`のプレースホルダーであり、実際のポリシーページは存在しない
   （④⑤で詳述）
4. 「確認メールを送信しました（本モックでは...）」の免責文言は、**実際に
   メール送信を実装した際には削除・更新が必要**（将来の実装忘れリスクとして記録）

## ④メールアドレスを本番取得する場合の必要情報

「本当に必要な最小限」と「将来あってもよい」を分離する。

### 必須（最小限）

| 項目 | 用途 |
|---|---|
| `email` | 連絡先そのもの |
| `company_slug` | どのレポート（会社）に対する登録か |
| `captured_at` | 取得日時（保存期間管理・監査に必要） |
| `consent` | 同意チェックボックスの状態（真偽値） |

### 将来あってもよい（今は不要、実装しない）

| 項目 | 用途 | 注意 |
|---|---|---|
| `company_name`（入力欄） | 任意入力の会社名・業種（既存フォームに既にある） | AI推定値の修正情報であり、個人情報ではない |
| `referrer` / 流入元 | マーケティング分析 | 取得する場合はどこまで追跡するか要検討 |
| `ip_address` | 不正登録対策 | それ自体が個人情報になりうるため慎重に |
| `unsubscribed_at` | オプトアウト管理 | 実装するなら必須級に格上げ |

**方針**: 上記「将来あってもよい」の項目は、実装する段になって初めて
「本当にこの用途に必要か」を再検討する。現時点では最小限（email・
company_slug・captured_at・consent）以外を保存しない設計を推奨する。

## ⑤個人情報・同意設計上の確認事項（実装前に要確認、法律判断はしない）

- **利用目的の明示**: 現在のチェックボックス文言「プライバシーポリシーに同意し、
  レポートの配信を希望します」は、配信同意はあるが、利用目的（誰が・何のために
  使うか）を利用者が確認できるプライバシーポリシー本体が存在しない
  （リンク先`#`）。本番化前にポリシーページの作成が必要
- **メール配信への同意**: 現状のチェックボックスは「レポートの配信」への同意のみ。
  営業連絡・メルマガ等、配信の種類が増える場合は同意の粒度を分ける設計が必要になりうる
- **オプトアウト**: `mailtoLink()`による「配信停止はこちら」リンクは既に存在する
  （`support@aor.example.jp`宛のmailto）。ただし実際にメール配信機能を実装する場合、
  受信者からのオプトアウト依頼を確実に反映する仕組み（配信リストからの除外）が
  別途必要になる
- **保存期間**: 現状未定義。メールアドレスをいつまで保持するかのポリシーが必要
- **削除依頼への対応**: 本人からの削除依頼を受けた場合の削除手順・確認方法が未定義
- **管理者権限**: 将来Review Dashboardにリード一覧を表示する場合、閲覧できる
  管理者の範囲（現状`ADMIN_USER`は1組のみ）をどう設計するか要検討
- **ログへのメール混入**: 今回の監査で、**現状のログにメールアドレスが
  混入する経路は存在しない**ことを確認済み（③の実測結果）。将来API化する際は、
  `redact.js`の対象パターンにメールアドレス自体は含まれていない点に注意
  （`redact.js`はAPIキー等のシークレット検出用であり、個人情報のマスキング用
  ではない。メールアドレスをログに書く設計にする場合は別途配慮が必要）
- **バックアップへの混入**: 同様に、将来リードデータをファイルとして保存する
  設計にした場合、`backup.js`がそのディレクトリも複製することになるため、
  バックアップ先（`backup/`ディレクトリ）のアクセス制御・保持期間も
  個人情報保護の対象として扱う必要がある

## ⑥保存方式候補比較

| 項目 | A. 自社サーバー保存 | B. 外部フォーム/CRM | C. メール配信サービス | D. 現状維持（無回収） |
|---|---|---|---|---|
| 実装コスト | 中（API・簡易ストレージ・Dashboard画面） | 低（埋め込みタグ程度） | 低〜中（API連携） | なし |
| 運用コスト | 中（自前でホスティング・保守） | 低（SaaS利用料） | 低〜中（配信数課金） | なし |
| セキュリティ | 自社の実装品質に依存（本プロジェクトは認証・CSRF等の基盤が既にあり有利） | 外部サービスのセキュリティに依存 | 同左 | 最も安全（データが存在しない） |
| 個人情報管理 | 自社で完全にコントロール可能、責任も自社 | 外部への委託（契約・DPA等が必要） | 同左 | 管理対象が無い |
| メール配信機能 | 別途実装が必要 | サービスによる（無い場合も） | 標準機能として提供 | 無し |
| 将来の拡張性 | 高（自社の他機能と統合しやすい） | サービス次第 | メール配信特化 | 低（回収自体をやり直す必要） |
| サービス依存 | 無し | あり（サービス終了・値上げリスク） | あり | 無し |
| 障害時の影響 | 自社サーバー障害時にリード取りこぼし | 外部サービス障害の影響を受ける | 同左 | 影響なし（そもそも回収しない） |
| APIキー等の管理 | 不要（自社内で完結） | 必要（外部サービスのAPIキー） | 必要 | 不要 |
| 本プロジェクトとの親和性 | **高**（server.js・auth.js・shared/の基盤を再利用可能） | 中（新規の外部連携コードが必要） | 中（同上） | 高（何もしなくてよい） |

## ⑦推奨する本番化方式

**短期（Phase1継続）**: **D（現状維持）を推奨**。実LLM/実検索providerの検証
（Task25/26から継続する既知の最優先事項）が完了し、実際にAIが生成する
レポートの質が確認できるまでは、メール回収を実装する優先度は低い。
「見せるものの質」が固まっていない段階でリード獲得の仕組みだけ先に作っても、
獲得したリードに送るべき本物のレポートが無い状態になる

**中期（実LLM検証完了後、実際にリード獲得を始める場合）**: **A（自社サーバー保存）
を推奨**。理由:
- 本プロジェクトには既に認証（`auth.js`）・監査ログ（`logAudit()`）・
  CSRF対策・`redact.js`・`backup.js`・`shared/json-file.js`など、
  Bで外部サービスに委託する場合でも結局自社側で必要になる基盤の多くが
  既に存在し、重複実装なく拡張できる
- B/Cは初期コストが低い一方、個人情報を外部委託することになり、
  委託先の選定・契約・データ処理契約（DPA相当）の検討が別途必要になる。
  本プロジェクトの現段階（実LLM未検証、正式リリース前）でその検討コストを
  払う価値が低い
- ただし「メール配信機能」自体（実際に確認メール・営業メールを送る機能）は
  自前で持つと実装コストが高いため、**保存はA（自社）、配信のみC相当の
  外部メール配信サービスを部分的に使う**というハイブリッドも将来的な
  選択肢になりうる（今回は結論を出さず、選択肢として記録するに留める）

## ⑧現在のコードベースで再利用できる仕組み

将来API化する際、新規の重複実装を避けるために再利用できるもの:

| 既存の仕組み | 再利用方法 |
|---|---|
| `website/aor-admin/server.js`のルーティング基盤 | 新しい`POST /api/leads`等のエンドポイントを同じパターンで追加できる。ただし`/api/health`と同様、**認証を要求しない公開エンドポイント**として設計する必要がある点に注意（実際の見込み客はDashboardへログインしていないため） |
| `auth.js`の`logAudit()` | リード取得イベントを`action:"lead_captured"`等として監査ログへ記録するパターンをそのまま流用できる。**メールアドレス自体はログに残さず、slug・成功可否・日時のみを記録する設計**を推奨（現状のログ設計方針と一貫させる） |
| `shared/redact.js` | 将来フリーテキスト項目（問い合わせ内容等）を追加する場合、ログ記録前に通す |
| `shared/json-file.js`（`writeJson`/`appendJsonLine`/`readJsonLines`） | リードをJSON Linesファイルとして保存する場合、そのまま使える（DBを持たない設計方針を維持できる） |
| `shared/paths.js` | `LEADS_DIR`等の新規パス定数を同じパターンで追加できる |
| `shared/config-validator.js`の設計パターン | 将来メール配信サービス（外部API）を使う場合、`checkLlmConfig()`と同じ「mock/実providerを環境変数で切替、APIキー未設定でも動く」という既存方針を踏襲できる |
| `backup.js`のTARGETS配列 | リードデータの保存先ディレクトリを1行追加するだけでバックアップ対象にできる（Task22→Task25で`aor-data`を追加した際と同じパターン） |
| `website/aor-admin/public/`のUIパターン（`list.js`・`detail.js`・`admin.css`） | 将来「リード一覧」画面を追加する場合、既存のテーブル表示・SSE自動更新（`broadcastReportsUpdate()`と同様の仕組み）のパターンをそのまま踏襲できる |
| `scripts/generator/shared/cli-utils.js`の`runCli()` | リードのエクスポート・一覧CLI等を作る場合の標準パターン |

**CSRFについての注意**: `auth.js`の現行CSRF実装はセッションCookieに紐づく
トークン方式であり、**ログイン済み管理者向けのAPI（Review Dashboard）を
前提にしている**。実際の見込み客（未ログインの匿名ユーザー）からの
`POST /api/leads`にこの仕組みをそのまま適用することはできない
（見込み客はセッションを持たない）。公開フォーム向けには、別の悪用対策
（レート制限・honeypot項目・Originヘッダー確認等、⑨参照）を新たに設計する
必要がある。

## ⑨将来API化する場合のセキュリティ要件（設計整理のみ、実装しない）

| 項目 | 方針の整理 |
|---|---|
| 認証 | 匿名の公開エンドポイントとする（見込み客はログインしない）。`/api/health`と同様、`auth.authenticate()`を経由しないルートとして実装する |
| CSRF | 匿名フォームには既存のセッションベースCSRFは適用できない。代わりにOriginヘッダー検証（`website/aor`のオリジンからのみ受け付ける）等を検討 |
| レート制限 | 現状未実装（Dashboard側にも無い、既知の未実装事項）。公開エンドポイントでは特に重要。同一IP・同一メールアドレスからの短時間大量送信を制限する仕組みが必要 |
| spam対策 | honeypot項目（人間には見えないダミー入力欄。botが埋めたら拒否）等、軽量な対策から検討 |
| email validation | 現状のHTML5`type="email"`によるクライアント側検証に加え、サーバー側でも形式検証が必要（クライアント側検証はバイパス可能なため） |
| duplicate handling | 同じslug×同じemailの重複登録をどう扱うか（上書き／エラー／許容）の方針決定が必要 |
| secret管理 | 外部メール配信サービスを使う場合のAPIキーは、既存の`config-validator.js`と同じ環境変数方式で管理し、ログに出さない（`redact.js`の対象パターンに配信サービス固有のキー接頭辞を追加することも検討） |
| ログのredact | メールアドレス自体をログに書き込まない設計を基本とする（上記④⑤参照） |
| 管理画面からの閲覧権限 | 既存の単一`ADMIN_USER`で足りるか、リード情報専用の閲覧権限を分けるべきかは、実装時に再検討 |
| 削除機能 | 本人からの削除依頼に対応するAPI・CLIが必要（未実装） |
| export機能 | 営業活動で使うためのCSV等エクスポート機能が必要になる可能性が高い（未実装） |
| audit log | `auth.js`の`logAudit()`パターンを流用し、「誰が・いつ・どのリードを閲覧/エクスポート/削除したか」を記録する |

## ⑫実装状況の更新（PJ2 第1実装: 保存基盤）

上記は本ドキュメント作成時点（Task27）では未実装だったが、その後の「PJ2：AOPメール
回収API 第1実装」で、⑦の推奨方式（A: 自社サーバー保存）に基づき、**保存のみ**を
スコープとした独立サーバー`website/aor-lead-api/`（詳細は同ディレクトリの
`README.md`参照）を実装した。以下、本ドキュメントの記述との差分・現状を記録する。

- `POST /api/leads`で`email`・`company_slug`・`captured_at`（サーバー生成、
  クライアント指定値は無視）・`consent`（厳密なboolean trueのみ許可）の4項目のみを

## ⑬実装状況の更新（PJ2 第2実装: 公開フォーム接続＋E2E）

⑫の保存基盤に対し、`website/aor/email-capture.js`から実際に`POST /api/leads`へ
接続する第2実装を行った。差分・現状は以下のとおり。

- **フロントエンド配線**: `email-capture.js`のフォーム送信ハンドラを非同期化し、
  `email`/`company_slug`/`consent`のみを送信するよう変更した（`captured_at`は
  従来どおりサーバー生成、送信しない）。送信先URLは`common.js`の`LEAD_API_BASE_URL`
  定数（`OPERATOR_EMAIL`と同じ「配置ごとに書き換える」方式）
- **UI**: 既存のUIデザインは変更していない。新規に表示領域を1つ追加したのみ
  （`#api-error`、既存の`#email-error`/`#consent-error`と同じ`.field-error`クラスを
  再利用）。429・5xx・通信エラーをそれぞれ異なる文言で表示し、400系エラーは
  サーバー側の固定文言（ユーザー入力を含まない）をそのまま表示する
- **二重送信防止**: submitボタンを送信中disabledにし、モジュール変数
  `isSubmitting`でも二重ガードする。永続的なidempotency機構は実装していない
  （⑨の想定どおり、今回は不要と判断）
- **honeypot**（⑨で未決事項としていたもの）: 既存フォームに自然に追加できたため
  実装した。`#hp-website`（オフスクリーン配置、`tabindex="-1"`、`aria-hidden`）に
  値が入っていればサーバー側で検知し、保存せず本物の成功と同じ`201`を返す
  （bot側に検知を悟らせないため）。`leads-audit.jsonl`に
  `action:"lead_honeypot_triggered"`として記録する
- **CORS**（⑨で「Originヘッダー検証を検討」としていたもの）: 許可リスト方式で実装した。
  環境変数`LEAD_API_ALLOWED_ORIGINS`で本番の許可Originを設定する（本番URL未確定のため
  決め打ちのデフォルトにはしていない。未設定時は`website/aor/README.md`のローカル
  動作確認手順に合わせた既定値のみ許可）。認証機構としては扱わない設計（詳細は
  `website/aor-lead-api/README.md`参照）
- **保存schema**: ⑫から変更なし。`email`/`company_slug`/`captured_at`/`consent`の
  4フィールドのみ。`ip`・`user_agent`・`referrer`等は追加していない
- **E2E**: このリポジトリにnpm依存・Playwrightが存在しないため（本プロジェクト全体の
  方針）、ブラウザを伴う自動E2Eテストは追加していない。代わりに実装時にClaude in Chromeで
  実際にフォーム送信を行い、正常系（成功UI・`leads.jsonl`への保存）・異常系
  （通信エラー、レート制限429、honeypot検知）・PII非漏洩（`leads-audit.jsonl`・
  サーバーのstdout/stderrにメールアドレスが出現しないこと）を手動で確認した。
  自動回帰は`scripts/generator/test/lead-api.test.js`（HTTPレベルの統合テスト、
  CORS許可リスト・honeypotのテストを含む）が担う

**引き続き未実装（今回のスコープ外）**: メール送信・営業フォロー、Adminでのリード
